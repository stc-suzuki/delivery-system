# 配送管理システム 設置・更新手順書

最終更新: 2026-11-20

## 1. この文書について

本番のサーバーに配送管理システムを入れて使い始めるまでの手順（2章）と、入れた後にプログラムを新しくする手順（3章）、うまくいかなかったときに前の状態へ戻す手順（4章）をまとめたものです。本番のサーバーを操作する担当者が、上から順に作業できるように書いています。

- サーバーは Windows と Linux のどちらでも動きます。違いがある手順は両方を書いています。決まった方だけ読んでください
- コマンドは、特に断りがなければシステムを置いたフォルダ（以下「システムのフォルダ」）で実行します。Windows は PowerShell、Linux は bash です
- `<…>` は、その場で決める値に置き換えてください
- 作業時間の目安：初めての設置は2〜3時間（HTTPSの準備を除く）、更新は15〜30分です
- 仕組みの詳しい説明は「仕様書」8章（開発・運用）にあります

**全体の流れ**

| 段階 | 作業 | 節 |
|---|---|---|
| 準備 | サーバー・ソフト・URLとHTTPSの証明書を用意する | 2.1 |
| 設置 | プログラムを置き、組み立て、DBと設定ファイルを用意して初期化する | 2.2〜2.6 |
| 起動 | 試しに起動し、自動で起動するように登録し、HTTPSの受け口をつなぐ | 2.7〜2.9 |
| 確認 | 画面とドライバーのスマホで動作を確かめる | 2.10 |
| 運用 | 毎日のバックアップを登録し、作業の記録を残す | 2.11・2.12 |

## 2. 初めて設置する

### 2.1 用意するもの

**サーバー**

| 項目 | 目安 |
|---|---|
| OS | Windows（Windows Server 2019 以降、または Windows 10/11）か Linux（Ubuntu 22.04/24.04 など） |
| CPU・メモリ | 2コア・メモリ4GB以上（組み立てに余裕を持たせるため） |
| ディスク | 20GB以上の空き（プログラムと部品で約1GB。残りはDB・バックアップ・記録用） |
| 台数 | 1台で足ります（トラック15台・配送先約1,000件・利用者約50人の規模で確認済み） |

**入れるソフト**

| ソフト | 版 | 用途 |
|---|---|---|
| Node.js | 20 以降の LTS 版（開発では 24 で確認） | プログラムを動かす |
| PostgreSQL | 16 を推奨（14 以降） | データベース。別のサーバーやクラウドのDBでもよい |
| Git | 新しいもの | プログラムを取得・更新する |

**ネットワーク**

- URL（例：`https://haisou.example.co.jp`）と、そのHTTPSの証明書。ドライバーのスマホの位置情報は、HTTPSでないとブラウザが送らないため必須です
- ドライバーは社外からスマホでつなぐため、外から443番（HTTPS）でこのサーバーに届く必要があります。システム自体が待ち受ける3000番は外に開けません（2.9節で受け口を前に置きます）
- サーバーから外へ：`msearch.gsi.go.jp`（国土地理院の住所検索。配送先の登録時に使う）、設置・更新のときに `github.com` と `registry.npmjs.org`
- 利用者のブラウザから外へ：`tile.openstreetmap.org`（地図の画像）、`unpkg.com`（地図のピンの画像）

**事前に決めておくこと**

- システムのフォルダ（例：Windows `C:\delivery-system`、Linux `/opt/delivery-system`）
- バックアップの保存先（DBと別のディスク、または社内のファイルサーバー）
- DBの名前・ユーザー名（以下、例として `delivery_db`・`delivery`）

### 2.2 プログラムを置く

GitHub のリポジトリ `stc-suzuki/delivery-system` から取得します（取得には読み取り権限のあるアカウントが必要です）。

```
git clone https://github.com/stc-suzuki/delivery-system.git <システムのフォルダ>
cd <システムのフォルダ>
git checkout main
```

- サーバーから GitHub につなげない場合は、開発側で用意したファイル一式（`.git` フォルダを含む）を写してもかまいません
- 以降のコマンドは、このフォルダで実行します

### 2.3 部品を入れて組み立てる

```
npm ci
npm run build
```

- `npm ci` は `package-lock.json` に書かれた版のとおりに部品を入れます（数分かかります）。組み立てに使う部品も必要なため、`--omit=dev` などは付けません
- `npm run build` は本番用に組み立てます（数分かかります）。最後に画面ごとの一覧が出て、エラーで止まらなければ成功です。途中の「Dynamic server usage」という表示はエラーではありません

### 2.4 データベースを作る

システム専用のDBユーザーとDBを作ります。パスワードは英字と数字だけにしてください（記号を使うと 2.5 節の接続先の書き方が変わるため）。

Windows（PostgreSQL の管理者 `postgres` で実行）：

```
& "C:\Program Files\PostgreSQL\16\bin\psql.exe" -U postgres -c "CREATE USER delivery WITH PASSWORD '<DBのパスワード>'"
& "C:\Program Files\PostgreSQL\16\bin\createdb.exe" -U postgres -O delivery delivery_db
```

Linux：

```
sudo -u postgres psql -c "CREATE USER delivery WITH PASSWORD '<DBのパスワード>'"
sudo -u postgres createdb -O delivery delivery_db
```

- DBは空のまま次へ進みます。テーブルは 2.6 節で作ります
- クラウドのDBを使う場合は、そのサービスの画面でDBとユーザーを作り、接続先（ホスト名・ポート）を控えます

### 2.5 設定ファイルを作る

システムのフォルダに `.env.local` という名前のファイルを作り、次の4行を書きます（文字コードは UTF-8）。

```
DATABASE_URL="postgresql://delivery:<DBのパスワード>@localhost:5432/delivery_db"
NEXTAUTH_URL="https://<本番のURLのホスト名>"
NEXTAUTH_SECRET="<下で作る値>"
HOSTNAME="127.0.0.1"
```

| 項目 | 書くこと |
|---|---|
| `DATABASE_URL` | 2.4 節で作ったDBの接続先。DBが別のサーバーなら `localhost` をそのホスト名にする |
| `NEXTAUTH_URL` | 利用者がブラウザで開く正式なURL（`https://` から始まる。末尾の `/` は付けない） |
| `NEXTAUTH_SECRET` | ログインの暗号鍵。次のコマンドで作った64文字の値を貼る（実行するたびに違う値になる） |
| `HOSTNAME` | `127.0.0.1` にすると、システムはこのサーバーの中からの接続だけを受け付ける（外からは 2.9 節の受け口を通る） |

```
npm run secret:generate
```

- このファイルには秘密の情報が入ります。担当者以外が読めない場所に置き、メール・チャットで送らないでください。控えはバックアップと別の安全な場所に置きます（仕様書 8.4・8.6 節）
- 待ち受けるポートを3000番から変える場合は `PORT="<番号>"` を足します
- 設定は、データベースの操作（2.6 節・3章）も含めてすべてこのファイルから読みます

### 2.6 初期化する

空のDBに、テーブル・システム管理者1人・システム設定の初期値だけを入れます。

```
npm run db:init-production
```

- 最後に「本番用の初期化が終わりました。」と出て、「システム管理者: （ログインに使う名前）」と「パスワード（自動で作成。…）: （パスワード）」が表示されます。この2つを控えてください。パスワードはこの1回しか表示されません
- 途中に出る「Update available 5.22.0 -> …」の枠は、部品の新しい版のお知らせです。表示されている更新コマンドは実行しないでください（版を上げるのは開発側で確かめてから行います）
- パスワードを自分で決める場合は、環境変数 `INIT_ADMIN_PASSWORD`（12文字以上）を指定して実行します
- DBに業務のデータが1件でもあると、件数を表示して何もせずに止まります（間違ったDBを指定したときの事故を防ぐため）。そのときは `DATABASE_URL` を確かめてください
- 試験用のトラック・配送先などは入りません。開発用の `npm run db:seed` は本番では使いません

### 2.7 試しに起動する

```
npm start
```

- 「Ready on http://127.0.0.1:3000」と出れば起動しています。サーバーの中のブラウザで `http://localhost:3000` を開き、2.6 節で控えた名前とパスワードでログインできることを確かめます
- 「[設定の誤り]」と出て止まった場合は、表示された理由に従って `.env.local` を直します（5章）
- 「[設定の注意] NEXTAUTH_URL が https ではありません」は、試験のために `http://` にしている間は出てかまいません
- 確かめたら Ctrl+C で止めます

### 2.8 自動で起動するように登録する

サーバーを再起動したときに、システムも自動で起動するようにします。

**Windows（タスク スケジューラ）**

1. タスク スケジューラで「タスクの作成」を開く
2. 全般：名前「配送管理システム」、「ユーザーがログオンしているかどうかにかかわらず実行する」を選ぶ
3. トリガー：「スタートアップ時」
4. 操作：プログラム `powershell.exe`、引数 `-ExecutionPolicy Bypass -File scripts\start-production.ps1`、開始（作業フォルダー）にシステムのフォルダ
5. 設定：「タスクを停止するまでの時間」のチェックを外す。「タスクが失敗した場合の再起動の間隔」を1分・3回にする（システムが異常終了したときに自動で立ち上げ直すため）
6. 作ったタスクを右クリックして「実行」し、`http://localhost:3000` が開くことを確かめる

- 画面に出る記録は `logs\server-年月日.log` に残ります（90日より古いものは起動時に消えます）
- **止めるときは、次のコマンドを使います**。タスク スケジューラの「終了」では、起動用のスクリプトだけが止まり、システム本体は動き続けてしまいます

  ```
  powershell -ExecutionPolicy Bypass -File scripts\stop-production.ps1
  ```

  「ポート3000 のシステムを止めました」と出れば止まっています。このコマンドで止めた場合は「失敗」扱いにならないため、上の自動の再起動は働きません
- 起動するときは、タスク スケジューラでタスクを「実行」します

**Linux（systemd）**

`/etc/systemd/system/delivery-system.service` を次の内容で作ります（`<実行ユーザー>` はシステムのフォルダの持ち主）。

```
[Unit]
Description=Delivery management system
After=network.target postgresql.service

[Service]
Type=simple
User=<実行ユーザー>
WorkingDirectory=/opt/delivery-system
ExecStart=/usr/bin/npm start
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

```
sudo systemctl daemon-reload
sudo systemctl enable --now delivery-system
sudo systemctl status delivery-system
```

- 記録は `journalctl -u delivery-system` で見られます
- 止める・起動する：`sudo systemctl stop delivery-system`／`sudo systemctl start delivery-system`

### 2.9 HTTPSの受け口を設定する

外からのHTTPS（443番）を受けて、このサーバーの3000番へ渡す受け口（リバースプロキシ）を前に置きます。受け口には次の2つが必要です。

- 元のホスト名（`Host`）をそのままシステムへ渡すこと（リアルタイム追跡の接続で、同じホストからの接続かを確かめているため）
- WebSocket を通すこと（リアルタイム追跡の地図が使う。`/api/socket`）

受け口のソフトは、社内で使い慣れたもの（IIS、nginx、Caddy など）でかまいません。設定例を付録Bに載せています。設定したら、社外のスマホから `https://<本番のURLのホスト名>` を開き、ログイン画面が出ることを確かめます。

### 2.10 動作を確かめる

1. パソコンのブラウザで本番のURLを開き、2.6 節のアカウントでログインする
2. システム設定画面で、本社の名前・住所・出発時刻・定時・積載利用率などを入力して保存する（住所を保存すると地図の本社の位置が決まります）
3. 試しにトラック・ドライバー・配送先を1件ずつ登録し、配送先が地図に出ることを確かめる（住所検索が動いていることの確認）
4. 当日の稼働トラックを登録し、配送計画一覧の「ドライバー用URLをコピー」で得たURLを、ドライバーのスマホで開く
5. スマホで「運送開始」を押し、リアルタイム追跡画面の地図にトラックが出ることを確かめる（位置情報とリアルタイム配信の確認）
6. 試しに登録したデータを消す（または本番のデータの登録へ進む）
7. 2.6 節のパスワードを変える場合は、利用者管理画面で変える。利用者・トラック・ドライバー・配送先・商品を登録する（配送先と商品は表計算ソフトのCSVで一括登録できます。操作はオペレーションマニュアル参照）

### 2.11 毎日のバックアップを登録する

DBのバックアップを毎日取るように登録します。手順の詳しい説明は仕様書 8.4 節にあります。

Windows：タスク スケジューラに次を登録します（トリガーは毎日21:00など業務の後、開始フォルダーはシステムのフォルダ）。

```
powershell.exe -ExecutionPolicy Bypass -File scripts\db-backup.ps1 -OutDir <バックアップの保存先> -KeepDays 30
```

Linux：`crontab -e` で次を登録します（毎日21:00の例）。

```
0 21 * * * pg_dump -h localhost -U delivery -Fc --no-owner --no-privileges -f <保存先>/delivery_db_$(date +\%Y\%m\%d).dump delivery_db
```

- DBのパスワードは、実行するユーザーのホームの `~/.pgpass` に `localhost:5432:delivery_db:delivery:<DBのパスワード>` と書き、`chmod 600 ~/.pgpass` で本人だけが読めるようにします
- 古いファイルは自動では消えないため、`find <保存先> -name '*.dump' -mtime +30 -delete` も同じように登録します

- 登録したら一度手で実行し、保存先にファイルができることを確かめます
- バックアップから実際に戻せるかを、月に1回、別のDBへ戻して確かめることをおすすめします（仕様書 8.4 節）

### 2.12 記録を残す

次のことを作業の記録（付録C）に書き、担当者が見られる場所に保管します。

- 設置した日・担当者
- 動かしているプログラムの版：`git log -1 --format="%h %ad" --date=short` の表示
- システムのフォルダ・DBの名前・バックアップの保存先
- `.env.local` の控えの置き場所（中身は書かない）

## 3. 更新する

開発側から新しい版を受け取ったときの手順です。システムを止める時間は10分ほどです。ドライバーが配送中の時間帯は避け、業務の終わった後に行ってください。

1. **今の版を控える**：`git log -1 --format="%h %ad" --date=short` の表示を記録する（戻すときに使う）
2. **システムを止める**：Windows は `powershell -ExecutionPolicy Bypass -File scripts\stop-production.ps1`（2.8 節）、Linux は `sudo systemctl stop delivery-system`
3. **DBのバックアップを取る**（戻すときに使う）：

   ```
   powershell -ExecutionPolicy Bypass -File scripts\db-backup.ps1 -OutDir <バックアップの保存先>
   ```

   - Linux は 2.11 節の `pg_dump` を手で実行する

4. **新しい版を取得する**：

   ```
   git fetch
   git checkout main
   git pull --ff-only
   ```

   - 「Not possible to fast-forward」などと出て止まった場合は、サーバー上でプログラムのファイルが書き換えられています。続けずに開発側に連絡してください（`git status` の表示を添える）

5. **部品を入れ直して組み立てる**：

   ```
   npm ci
   npm run build
   ```

6. **DBの変更を反映する**：

   ```
   npm run db:deploy
   ```

   - 「No pending migrations to apply.」なら変更はありません。「All migrations have been successfully applied.」なら反映されました
   - 何度実行しても、反映済みのものは繰り返しません

7. **システムを起動する**：Windows はタスクを「実行」、Linux は `sudo systemctl start delivery-system`
8. **確かめる**：ログインして、ダッシュボード・荷物受付・配送計画一覧を開く。開発側から確認する点を指示された場合は、それも確かめる
9. **記録する**：新しい版（手順1と同じコマンドの表示）と日時を作業の記録に書く

- 更新してもログイン中の人がログアウトされることはありません（暗号鍵を替えない限り）
- 開発側から「設定ファイルに項目を足す」などの指示がある場合は、手順5と6の間で行います

## 4. 元に戻す

更新後にシステムが動かない、または業務に支障が出たときは、更新前の状態に戻します。

1. システムを止める（3章の手順2と同じ）
2. プログラムを前の版に戻す：

   ```
   git checkout <3章の手順1で控えた版>
   npm ci
   npm run build
   ```

3. 更新で `npm run db:deploy` がDBの変更を反映していた場合だけ、DBを3章の手順3のバックアップに戻す（「No pending migrations」だった場合は不要）：

   ```
   powershell -ExecutionPolicy Bypass -File scripts\db-restore.ps1 -File <バックアップ>.dump -TargetDb delivery_db -Overwrite
   ```

   - Linux は仕様書 8.4 節の `pg_restore` のコマンドで戻す

4. システムを起動して、ログインと主な画面を確かめる
5. 開発側に、何が起きたか（画面の表示、`logs` の記録）を伝える。直った版を受け取ったら、改めて3章の手順で更新する

- DBを戻すと、バックアップを取った後の入力（受付・配達完了など）は失われます。更新の直前に取ったバックアップを使えば、失われる分はほとんどありません
- 前の版に戻した後は `git checkout main` で最新の版に戻るまで、`git pull` だけでは新しい版になりません。次の更新は3章の手順4から行えば問題ありません

## 5. 困ったとき

| 症状 | 確かめること |
|---|---|
| 起動しない。「[設定の誤り] NEXTAUTH_SECRET …」と出る | `.env.local` の暗号鍵が無いか短い。`npm run secret:generate` の値を貼る（2.5 節） |
| 起動しない。「Could not find a production build」と出る | 組み立てていない。`npm run build` を実行する |
| 起動しない。「[起動の失敗] ポート3000は別のプログラムが使っています」と出る | 前に起動したシステムが動いたままになっている。Windows は `scripts\stop-production.ps1` で止めてから起動し直す。別のソフトが使っている場合は `.env.local` の `PORT` を変える（受け口の渡し先も合わせて変える） |
| 止めたはずなのに画面が開く | Windows でタスク スケジューラの「終了」だけを行った。`scripts\stop-production.ps1` で止める（2.8 節） |
| 画面に「サーバーエラー」が出る、DBにつながらない | PostgreSQL が動いているか、`DATABASE_URL` のユーザー名・パスワード・DB名が正しいか |
| ログインしてもすぐログイン画面に戻る | `NEXTAUTH_URL` が、ブラウザで開いているURLと同じか（`https`、ホスト名、末尾の `/` なし） |
| リアルタイム追跡の地図にトラックが動かない | 受け口が WebSocket を通しているか、`Host` をそのまま渡しているか（2.9 節） |
| ドライバー画面で位置情報が送られない | HTTPSで開いているか。スマホの設定でブラウザに位置情報を許可しているか |
| 配送先の住所が地図に出ない | サーバーから `msearch.gsi.go.jp` につながるか |
| 地図が灰色で何も出ない | 利用者のブラウザから `tile.openstreetmap.org` につながるか |
| `npm run db:init-production` が止まる | DBに既にデータがある（2.6 節）。指定したDBが正しいか確かめる |

記録の場所：Windows は `logs\server-年月日.log`、Linux は `journalctl -u delivery-system`。開発側に問い合わせるときは、症状が出た時刻とその前後の記録を添えてください。

## 付録A 設定ファイル（.env.local）の見本

```
# データベースの接続先
DATABASE_URL="postgresql://delivery:<DBのパスワード>@localhost:5432/delivery_db"
# 利用者が開く正式なURL（https、末尾の / なし）
NEXTAUTH_URL="https://haisou.example.co.jp"
# ログインの暗号鍵（npm run secret:generate で作る。他の環境と使い回さない）
NEXTAUTH_SECRET="<64文字の値>"
# このサーバーの中からの接続だけを受け付ける（外からはHTTPSの受け口を通る）
HOSTNAME="127.0.0.1"
# 待ち受けるポート（省略すると3000）
# PORT="3000"
```

## 付録B HTTPSの受け口の設定例

どれも「受け口が443番でHTTPSを受け、`127.0.0.1:3000` へ渡す」設定です。証明書の入手・更新の方法は、使うソフトと社内の決まりに従ってください。

**Caddy**（証明書の取得と更新を自動で行う。Windows・Linux とも1つのファイルで動く）

```
haisou.example.co.jp {
    reverse_proxy 127.0.0.1:3000
}
```

- Caddy は `Host` と WebSocket をそのまま通すため、追加の設定はいりません
- 自動の証明書取得には、外から80番・443番でこのサーバーに届くことが必要です

**nginx**

```
server {
    listen 443 ssl;
    server_name haisou.example.co.jp;
    ssl_certificate     /etc/ssl/certs/haisou.crt;
    ssl_certificate_key /etc/ssl/private/haisou.key;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

**IIS**（Windows）

- 「URL 書き換え」と「Application Request Routing」を入れ、サイトのバインドに443番と証明書を設定し、`http://127.0.0.1:3000/{R:1}` へ渡す規則を作ります
- サーバーの役割で「WebSocket プロトコル」を有効にします
- Application Request Routing の「プロキシ」設定で「応答ヘッダーの場所を書き換える」は無効のままにし、元のホスト名を渡すよう `preserveHostHeader` を有効にします
