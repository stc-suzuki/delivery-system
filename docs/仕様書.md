# 配送管理システム 仕様書（現状実装まとめ）

最終更新: 2026-10-15（`main` ブランチ時点のコードを基に作成。10-15の変更＝商品の削除とCSV一括登録、配送先CSVの改善、荷台寸法の必須化と容積上限の自動計算、積載利用率の全体適用、ダッシュボードの帰社表示を反映）

本書は開発・保守を担当する方向けの技術仕様です。日常の操作方法は `docs/オペレーションマニュアル.md` を参照してください。ファイルの場所はリポジトリのルートからの相対パスで記載しています。

## 1. 概要

栃木県内の配送業務を対象とした社内向けWebシステム。その日に届ける配送先と荷物を受け付け、トラックへ割り当て、配送ルート（順番と到着予定時刻）を決め、配送中の進み具合をリアルタイムに追跡する。

- 管理者・配送管理者・事務担当者はPCブラウザで管理画面を使う
- ドライバーはスマートフォンから、ログイン不要の専用URLで担当ルートを確認し、配達完了などを報告する
- トラックへの積載は体積（m³）と荷台の寸法で判定し、AIによる割当案（参考）を提示する。1台のトラックが1日に何度も本社と往復する「複数便」に対応する

### 1.1 業務の流れ

1. **稼働トラックの登録**（配送管理者）: 配送日ごとに、使うトラックとドライバーの組み合わせを登録する
2. **荷物受付**（一般ユーザー以上）: 配送日ごとに、届ける配送先と荷物（商品・個数）を登録する。この時点ではどのトラックにも割り当てない（未割当＝プール）
3. **配送計画の作成**（配送管理者）: 未割当の配送先を各トラック・各便へ割り当てる。AI提案を参考にしてもよい。割当のたびにルートの順番と到着予定時刻が自動で計算し直される
4. **配送**（ドライバー）: 専用URLから運送開始、配達完了・スキップ、給油記録、帰社を報告する。位置情報は自動で送信される
5. **追跡**（一般ユーザー以上）: リアルタイム追跡画面で各トラックの位置と進み具合を確認する。ドライバーが押し忘れた操作は本部が代わりに行える
6. **稼働中の追加**（配送管理者）: 出発後に受け付けた配送先も、稼働中のトラックへ追加できる。この場合はドライバーが本社へ戻って積み直す前提で時刻を計算する

## 3. 認証・権限

### 3.1 ログイン

- `src/lib/auth.ts`: NextAuthのCredentials認証。**名前**とパスワードで `User` テーブルを照合し、bcryptで検証する（メールアドレスではない）。セッションはJWTで、`role` をトークンとセッションに持たせる
- ログイン画面（`src/app/(auth)/login/page.tsx`）は、ログイン前に開こうとしていた画面（`callbackUrl`）へ戻る。外部サイトへ飛ばされないよう、`/` で始まる（`//` で始まらない）場合だけ使い、それ以外は `/dashboard` へ移る

### 3.2 権限（3段階）

| 権限 | 表示名 | 使える範囲 |
|---|---|---|
| `STAFF` | 一般ユーザー | ダッシュボード、荷物受付、配送計画一覧（閲覧）、リアルタイム追跡 |
| `DELIVERY_ADMIN` | 配送管理者 | 上記に加えて、配送計画の作成・編集、稼働トラックの登録、荷物受付状況の確認 |
| `SYSTEM_ADMIN` | システム管理者 | 上記に加えて、ドライバー・トラック・配送先・商品・ユーザーの管理、システム設定 |

### 3.3 ミドルウェア（`src/middleware.ts`）

画面と API の両方に掛かる。

- **画面**: 未ログインは `/login` へ転送（戻り先は相対パスで付与）。権限が足りない画面は `/dashboard` へ転送
- **API**（`/api/...`）: 未ログインは 401、権限不足は 403 をJSONで返す
  - 参照（GET）は原則として一般ユーザーから可（荷物受付やサイドバーもマスタ・配送計画を読むため）。ただし `/api/users` はGETを含めシステム管理者のみ
  - マスタ（`/api/locations`・`/api/drivers`・`/api/trucks`・`/api/products`・`/api/settings`）の変更はシステム管理者のみ
  - 配送計画（`/api/plans`・`/api/stops`）の変更は配送管理者以上
  - 荷物受付の保存（`PUT /api/pool`）は一般ユーザーから可
- **ログイン不要で通すAPI**: `/api/auth/*` と、ドライバー画面が呼ぶものだけ（`/api/driver/*` のGET・PATCH、`/api/tracking` のPOST、`/api/tracking/stops/*` のPATCH、`/api/tracking/fuel` のPOST、`/api/tracking/fuel/*` のDELETE）

新しいAPIを追加するときは、この区分に当てはまるか、ドライバー画面から呼ぶなら `isPublicApi` に足す必要があるかを確認すること。

### 3.4 ドライバー用URL（`src/lib/driverAccess.ts`）

- `/driver/[routeId]` はログイン不要。ルートIDを知っていれば開けるURL方式で、配送計画一覧の「ドライバー用URLをコピー」で取得し、配送管理者がドライバーへ共有する
- 流出時の被害を抑えるため、**ログインしていない場合は、そのルートの配送日（日本時間）の当日しか使えない**。当日以外は403（`expired: true`）を返し、ドライバー画面は期限切れの案内を表示して位置送信と自動更新を止める。日本時間の0時を過ぎると配送中でも使えなくなる
- ログイン済みの利用者（リアルタイム追跡画面からの本部の代理操作）は日付に関係なく使える
- 「本部が代理で操作した」という記録（`actor: 'DISPATCHER'`）は、ログイン済みの場合だけ認める
- ドライバー用のルート情報では、ドライバーの電話番号・免許証番号などは返さない（名前のみ）

### 3.5 リアルタイム配信の認証（`server.ts`）

Socket.io（`/api/socket`）はNextのミドルウェアより手前で受け付けるため、接続時に `server.ts` 側でNextAuthのセッションCookieを検証し、未ログインの接続を拒否する。あわせて、Originヘッダーが同じホストの接続だけを受け付ける（WebSocketはCORSの制限を受けないため）。

### 3.6 初期アカウント

`prisma/seed.ts` が名前 `管理者` / パスワード `admin1234` のシステム管理者を作成する。開発用の値のため、本番では必ず変更すること。

## 4. データモデル（`prisma/schema.prisma`）

### 4.1 マスタ

| モデル | 内容 | 主な項目 |
|---|---|---|
| `User` | 社内ユーザー | `name`（一意・ログインに使う）、`email`（一意）、`password`、`role` |
| `Driver` | ドライバー | `name`、`phone`、`type`（固定ルート/専任/営業）、`licenseNo`、`status`（`ACTIVE`/`INACTIVE`） |
| `DriverDayOff` | 平日の個別休日 | `driverId`、`date`。土日・祝日はコード側で休日扱いのため保存しない |
| `Truck` | トラック | `plateNo`、`model`、`capacityKg`（登録・表示のみで計算には使わない）、`bedWidth`/`bedDepth`/`bedHeight`（荷台内寸、m。画面・APIでは必須）、`capacityM3`（積載可能容積。荷台寸法から自動計算して保存する）、`status`、`defaultDriverId` |
| `Location` | 配送先 | `name`、`address`（入力した住所）、`formattedAddress`（住所検索で一致した場所の名前。番地まで一致しないと町名・市までになる）、`phone`、`lat`、`lng`、`city` |
| `Product` | 商品 | `name`、`width`/`depth`/`height`（寸法、m） |
| `SystemSetting` | システム設定（1行のみ、`id`は`"default"`） | 5.15節参照 |

**論理削除**: 配送の履歴が残っているドライバー・トラックは外部キーの都合で物理削除できないため、削除操作では `Driver.status = INACTIVE`、`Truck.status = RETIRED` にする。削除済みは編集できず、一覧では薄いグレーで表示する。配送先は使われている場合は削除自体を拒否する。商品は物理削除する。ただし本日以降（日本時間）の未完了の停車地の荷物で使われている商品は削除を拒否する（荷物受付は商品の紐付けがない荷物を保存時に捨てるため）。過去の荷物は商品名・寸法を自分で持っているので、紐付け（`productId`）が外れるだけで表示に影響しない。ユーザーは常に物理削除。

### 4.2 配送

| モデル | 内容 |
|---|---|
| `PlanRoute` | **トラック1台×1日の配送ルート**。このシステムの管理単位。`truckId`、`driverId`、`routeDate`、`departureTime`、`status`（`PENDING`/`IN_PROGRESS`/`COMPLETED`）、`returnedAt`（帰社日時）、`startedByDispatcher`/`returnedByDispatcher`（本部による代理操作か） |
| `RouteTrip` | ルートの中の**便**（本社を出て戻るまで）。`tripIndex`（0始まり）、`departureTime`、`status`、`returnedAt`。**ルートは必ず1便以上を持つ** |
| `DeliveryStop` | 1日・1配送先の配送（停車地）。下記参照 |
| `Package` | 停車地に積む荷物1個。`name`、`width`/`depth`/`height`、`productId`（商品から選んだ場合）。体積は都度計算する。商品の寸法は登録時点の値をコピーして持つため、商品を後で編集しても過去の荷物は変わらない |
| `TrackingLog` | ドライバーの位置情報の履歴。`routeId`、`tripId`、`lat`、`lng` |
| `FuelLog` | 給油記録。`routeId`、`tripId` |

**DeliveryStop の主な項目**

- `stopDate`: 配送日。未割当の間も必須
- `routeId` / `tripId`: 割当先のルート・便。**両方null＝未割当（プール）**
- `stopOrder`: ルート内の順番
- `requestedArrivalTime`: お客様と約束した到着希望時刻。利用者が入力したときだけ変わり、ルートの再計算では上書きしない
- `scheduledTime`: 現在の計算による到着予定時刻
- `hasTimeConflict`: 移動時間の都合で到着希望時刻に間に合わない場合に立つ
- `arrivedAt`: 実際に配達完了した時刻
- `status`: `PENDING`（未完了）/`COMPLETED`（完了）/`SKIPPED`（スキップ。荷物はトラックに残っているものとして扱う）
- `version` / `updatedByName`: 荷物受付の同時編集対策（楽観ロック）
- `addedAfterDeparture`: 稼働開始後に追加された停車地か。trueの場合だけ「未割当に戻す」の対象
- `statusSetByDispatcher`: 配達状況を最後に変えたのが本部の代理操作か

**同じ配送先・同じ日の停車地**は原則1件。1台に積みきれない場合は、未割当の停車地を明示的に「分割」したときだけ2件以上になる。

### 4.3 廃止した概念

- `DeliveryPlan`（複数トラックを束ねた「配送計画」）は2026-07-29に廃止した。画面上の「配送計画」は、同じ日の `PlanRoute` の集まりを指す
- 下書き/確定の2状態（`PlanRoute.confirmedAt`）は2026-08-27に廃止した。状態は `RouteStatus`（稼働前/進行中/完了）だけで表す
- 停車地ごとの荷量割合（`cargoRatio`）は廃止した。積載は荷物の体積で判定する

## 5. 画面構成・機能一覧

### 5.1 ログイン（`/login`）

名前とパスワードでログインする。成功後、ログイン前に開こうとしていた画面（なければダッシュボード）へ移る。

### 5.2 サイドバー（`src/components/ui/Sidebar.tsx`）

権限に応じて3つの区分を表示する。

- 業務メニュー（全員）: ダッシュボード / 荷物受付 / 配送計画一覧 / リアルタイム追跡
- 配送管理（配送管理者以上）: 配送計画の作成 / 稼働トラックの登録 / 荷物受付状況の確認（注意が必要な日数をバッジ表示）
- マスタ管理（システム管理者）: ドライバー管理 / トラック管理 / 配送先管理 / 商品管理 / ユーザー管理 / システム設定

### 5.3 ダッシュボード（`/dashboard`）

日付を指定して、その日の状況を表示する（初期値は当日）。

- KPIカード（1行表示）: ルート数、完了、進行中、未割当トラック
- ドライバー稼働状況: 待機中 / 進行中 / 配達完了の3つの欄に分けて表示する（画面幅1280px以上で3つ横並び、1024〜1279pxは2つ並び）。進行中は「N/M便」バッジ
  - 配達完了の欄だけは、ドライバー・トラック・帰社の3列で1行に並べる（区分の列は出さない）。帰社の列は「帰社途中 HH:mm予定」（オレンジ系）か「帰社済み HH:mm」（緑系）
- 本日の配送ルート: ルートごとのカード。停車地一覧に便番号、運行状況のバッジ。配達完了のカードには、同じ「帰社途中／帰社済み」をカード幅の帯で表示する（表示は `src/components/dashboard/ReturnStatus.tsx` で共通化）
- 帰社途中の帰社予定時刻は6.7節の方法で求める
- API: `GET /api/dashboard?date=YYYY-MM-DD`（帰社途中のルートには `returnEta` を付ける）

### 5.4 荷物受付（`/pool`）

配送日を選び、その日に届ける配送先と荷物を登録する。トラックへの割当は行わない。

- 配送先の検索・選択、到着希望時刻、荷物の追加（商品を選び、個数を指定すると保存時にその数だけ荷物を登録する）
- 登録できるのは、本日以降でトラックが1台でも登録されている日まで
- 既に割当済み・分割済みの配送先は、バッジを表示して編集できないようにする
- その日の容積の見込み（登録済みトラックの容積上限の合計×想定往復回数×積載利用率に対する使用量）と、定時までに配り終えられるかの見込み（本社帰着予定）を表示する
- 保存は差分方式（追加・更新・削除した行だけを送る）。他の人が先に更新した行を上書きしようとすると拒否し、誰が更新したかを表示する（楽観ロック）
- API: `GET/PUT /api/pool`、`GET /api/pool/calendar`、`GET /api/plans/dates`

### 5.5 配送計画一覧（`/plans`）

日付を指定して、その日の全ルートを配車表（ガントチャート、`src/components/plans/DispatchGanttChart.tsx`）で表示する。

- 1トラック1行。出発、各停車地、本社経由（積み込み）、帰社のマーカーを時間軸上に表示。表示範囲は8:00〜20:00で、昼休みの時間帯を斜線で示す
- 完了した区間は緑色。帰社実績がある場合は実績の時刻、ない場合は推定の帰社予定を表示する
- 複数便のルートは、便ごとの区切りと本社経由を表示する
- 行を展開すると停車地ごとの荷物（同じ商品は「×個数」でまとめる）を確認できる
- 「ドライバー用URLをコピー」ボタン
- 行をクリックすると配送計画の作成（編集）画面へ移る（配送管理者以上）

### 5.6 配送計画の作成（`/plans/new`）

カレンダーから配送日を選ぶ入口の画面。各日の配送件数と未割当の有無をカレンダーに表示する。選んだ日に稼働前のトラックがあればその編集画面へ、すべて稼働中なら配送計画一覧へ案内する。

### 5.7 配送計画の作成・編集（`/plans/[id]`、`[id]` はルートID）

開いたルートの状態で、2つの画面に分かれる。

**稼働前（その日の稼働前のトラックすべてが対象）**

- 使用中のトラック一覧と、トラックごとの便（「＋便を追加」「－便を削除」。最後の1便は削除できず、配送先が残っている便も削除できない）、積載率と容量超過のバッジ（容積上限×積載利用率を100%とする）
- 商品の割当: 未割当の配送先を、プルダウンで各トラック・各便へ手動で割り当てる。割当済みの配送先は「未割当に戻す」ことができる
- AI提案: 未割当の配送先ごとに推奨のトラックを表示する（参考。保存はしない）。「参考の割当案をすべて反映」で一括反映できる。荷台に入らない配送先は「サイズ超過」、空きがない場合は「容積不足」と表示する
- 分割: 荷物が2個以上ある未割当の配送先を、荷物単位で2つの停車地に分けられる
- トラックの削除: 割り当てていた配送先は削除せず、未割当に戻す
- 割当を変えるたびに、そのルートの順番と到着予定時刻を計算し直して保存する（`src/lib/routeReorder.ts`）
- 手動割当では容積・サイズのチェックは行わない（AI提案の表示は参考扱い）

**稼働後（そのトラック1台だけが対象、「稼働後ルートの編集」）**

- 配送先の割当: その日の未割当の配送先を、このトラックへ追加する。新しく追加した場合は、ドライバーが一旦本社へ戻り、積み込み（設定の積み込み時間）をしてから出発する前提で到着予定時刻を計算し直す。現在地は最新の位置情報、なければ直近に配達完了した地点（実際の完了時刻順）、帰社済みなら本社とする
- 稼働開始後に追加した配送先だけ「未割当に戻す」ことができる（出発時から積んでいた荷物は対象外）
- ドライバーの変更（確認ダイアログあり）。トラックの変更はできない
- 完了済みのルートにも追加できる。追加するとルートは進行中に戻り、帰社記録はリセットされる
- 容積・サイズの超過、到着希望時刻に間に合わない場合は警告を表示する（保存は止めない）

共通:

- 編集できるのは、当日から「配車計画の先行登録可能日数」先までのルート（`src/lib/planEditPolicy.ts`）。当日は注意表示を出す
- 「トラックの削除」は稼働前の画面にのみある。運送開始済みのルートを画面から削除する手段はない

### 5.8 稼働トラックの登録（`/truck-schedule`）

配送日ごとに、使うトラックとドライバーの組み合わせを登録する。

- カレンダーに各日の登録台数を表示。登録できるのは当日から先行登録可能日数の範囲内。設定により土日・祝日を除外できる
- トラックを選ぶとデフォルトドライバーが入る。ドライバーの休日・他トラックとの重複をチェックする
- 前営業日と同じ構成を呼び出せる
- 対象は稼働前のルートだけ。チェックを外したトラックに割り当てていた配送先は、未割当に戻してからルートを削除する
- 新しいルートには必ず1便目を作る
- API: `POST /api/plans/batch`、`GET /api/plans/calendar`

### 5.9 荷物受付状況の確認（`/capacity-overview`）

当日から先行登録可能日数分の各日について、容積の使用率（80%以上で注意）と、容積超過・定時超過の見込みを一覧で表示する。判定は荷物受付と同じ。

### 5.10 リアルタイム追跡（`/tracking`）

- 当日の全ルートの一覧（15秒ごとに再取得）。ルートごとの状態と完了件数
- 地図（`src/components/map/TrackingMap.tsx`）: Socket.ioで受信した位置情報を元に、トラックのアイコンを移動させる
- 本部による代理操作: ドライバーが押し忘れた運送開始・配達完了・帰社（とその取り消し）を本部が代わりに行える。ドライバー画面には「本部による操作」と表示される

### 5.11 ドライバー用画面（`/driver/[routeId]`）

- ログイン不要。配送日の当日だけ使える（3.4節）
- ヘッダーに車両ナンバー、配送日、ドライバー名、進捗
- 停車地のカード: 到着予定時刻（時刻指定か目安かを区別）、住所、電話（タップで発信）、地図リンク。「完了」「スキップ」「取消」
- 複数便のルートは便ごとにまとめて表示し、「N便を開始」「この便を完了して本社へ」で進める。進行中でない便の停車地は操作できない
- 「運送開始」、すべての配送先が完了した後の「帰社」
- 給油記録の登録と取り消し
- 位置情報の共有（`navigator.geolocation.watchPosition`）。**HTTPSでないと動かない**（開発中の `localhost` だけは例外）
- 30秒ごとに最新の内容を取得し、配送先の構成が変わった場合はバナーと振動で知らせる。ルートが削除された場合は配送中止の案内を表示する

### 5.12 ドライバー管理（`/drivers`、`/drivers/[id]`）

種別（固定ルート/専任/営業）ごとの一覧、登録・編集・削除（履歴がある場合は非稼働化）。休日設定画面で、平日の個別休日をカレンダーから設定する（土日・祝日は自動で休日）。

### 5.13 トラック管理（`/trucks`）

登録・編集・削除（履歴がある場合は廃車扱い）。ナンバー、型式、積載量（kg）、荷台の幅・奥行き・高さ（必須、0より大きい数値）、状態、デフォルトドライバー（削除済みのドライバーは選択肢に出さない）。

- 容積上限（m³）は入力させず、荷台の幅×奥行き×高さから自動で計算して表示する（小数第3位で丸める）。APIもリクエストの容積上限は受け取らず、保存のたびにサーバー側で同じ計算をする（`resolveTruckBed`）。更新時は、送られなかった辺を現在の値で補い、3辺がそろわなければ400を返す
- 積み込み時の隙間によるゆとりは、トラックごとではなくシステム設定の「積載利用率」で一括して持たせる（6.1節）

### 5.14 配送先管理（`/locations`）・商品管理（`/products`）・ユーザー管理（`/users`）

- 配送先: 登録・編集・削除（使われている配送先は削除不可）。「住所確認」で緯度経度をプレビューしてから登録する。住所から市区町村を自動で取り出す
  - 一覧の住所欄は入力した住所（`address`）を表示する。住所検索で番地まで一致しなかった配送先は、「地図上の位置は『…』付近（番地まで特定できませんでした）」と添える（一致した名前に数字・丁目・番が無く、入力した住所と違う場合）。この配送先は地図上の位置が町・市の代表地点になり、距離・到着予定もその位置で計算される
  - CSV一括登録: 見出しは `name,address,phone` または `名称,住所,電話番号`（`名前`・`配送先名`・`電話`・`TEL` も可）。見出しが無ければ「名称,住所,電話番号」の列順として1行目から読む。行ごとに成否を表示する（6.8節）
- 商品: 名前と寸法の登録・編集・削除（4.1節の削除の条件あり）。荷物受付で荷物を追加するときに選ぶ
  - CSV一括登録: 見出しは `商品名,幅,奥行き,高さ`（英語、単位付きの `幅(m)` なども可）。見出しが無ければその列順として読み、後ろの体積などの列は読まない（商品マスタのExcelと同じ並び）。寸法は0より大きい数値（全角数字も可）。同じ名前の商品が既にある行は二重登録を防ぐため登録しない（寸法の変更は画面の編集で行う）
- ユーザー: 名前・メールアドレス・パスワード・権限の登録・編集・削除

### 5.15 システム設定（`/settings`）

| 項目 | 既定値 | 用途 |

| 昼休み時間 | 12:00〜13:00 | 6.3節の時刻計算 |
| 運送終了時間（定時） | 17:00 | 定時超過の判定 |
| 配送先での積み下ろし時間 | 10分 | 停車地ごとの作業時間 |

## 6. 計算ロジック（`src/lib`）

いずれも画面やDBに依存しない純粋関数として書かれており、自動テストの対象になっている（8章）。

### 6.1 積載の判定（`loadCapacity.ts`）

- **荷台に入るか**（`fitsBed`）: 荷物と荷台の3辺をそれぞれ小さい順に並べ、荷物の各辺が荷台の対応する辺以下なら入る（向きを変えて置くことは許す。実際の3D配置計算はしない）。停車地は荷物が全部入って初めて入るとみなす
- **容積上限**（`resolveTruckBed`）: トラックの容積上限は荷台の幅×奥行き×高さ（5.13節）
- **実効の上限**（`effectiveCapacityM3`）: 容積上限×積載利用率（システム設定）。容積の判定はすべてこの値を上限にする。容積上限が未設定のトラック（荷台寸法を必須にする前の古いデータ）は制約なしとして扱う
- **容積**（`checkCapacityOverflow`）: 停車地の荷物の体積合計と、実効の上限を比べる
- 容積の判定では、配達完了した停車地の荷物は数えない。スキップした停車地の荷物はトラックに残っているものとして数える
- 複数便のルートでは、容積・サイズの判定は便ごとに行う

### 6.2 AI提案の割当（`loadAssignment.ts` の `assignStopsToTrucks`）

未割当の配送先を、その日の稼働前のトラック×便（スロット）へ振り分ける参考案を作る。

- 配送先を本社から見た方位角の順（スイープ法）に処理し、同じ方面をなるべく同じ便にまとめる
- 「その日の総体積÷便の総数」を各便の目安量とし、今の便が目安量に達したら目安量未満の他の便へ切り替える（1台目への偏りを防ぐ）。1件で目安量を超える大きな荷物は、既に積み始めた便ではなく空いている便へ回す
- 切り替え先の選び方は設定で変えられる: 方面優先のみ（次の便）／方面優先＋積載バランス調整（積載率が最も低い便、既定）
- 到着希望時刻に矛盾しない便を優先する
- 各便に積める量は実効の上限（容積上限×積載利用率）。既に割り当て済みの荷物の体積を考慮する。**既存の便の範囲内でしか振り分けず、便を勝手に増やさない**。入らない分は「容積不足」、どのトラックの荷台にも入らない分は「サイズ超過」として積み残す
- API: `GET /api/plans/[id]/suggest`（参考表示のみ）、`POST /api/plans/[id]/assign-suggested`（一括反映）

### 6.3 ルートの順番と到着予定時刻（`routeOptimizer.ts`）

- 本社の座標はシステム設定の値を使う（初期値は `TOCHIGI_DEPOT`）
- **距離と移動時間**: 2点間の直線距離（ハーバサイン公式）÷平均時速30km
- **順番**（`orderWithTimeBudget`）: 到着希望時刻のある停車地を早い順に並べ、そこへ間に合う余裕がある限り、近くの時刻指定なしの停車地を途中に入れる。残りは近い順（最近傍法）
- **到着予定**（`estimateStopTimes`）: 出発時刻から移動時間と積み下ろし時間を積み上げる。到着希望時刻に間に合う場合は希望時刻を到着予定にし、間に合わない場合は最短の時刻にして矛盾ありとする
- **本社帰着**（`estimateReturnToDepotTime`）: 最後の停車地の積み下ろし後、本社へ戻る時刻。配送計画一覧の帰社予定、荷物受付の定時超過判定はこの時刻を使う
- **昼休み**（`addTimeOutsideLunch`）: 昼休みは運転・積み下ろし・積み込みのすべてを止めて休む。途中で昼休みに入れば昼休みの長さだけ終わりが遅れ、昼休み中に始めようとした場合は休憩明けに始める。ちょうど昼休み開始に到着した場合は、休憩明けから積み下ろしする
  - 例: 11:40発・30分の移動→13:10着。11:40着・積み下ろし45分→13:25発。11:59本社着・積み込み30分→13:29発
- 1ルートあたりの停車地は最大40件（`MAX_STOPS_PER_ROUTE`）
- 配送計画一覧の帰社予定は、最後の停車地の**予定時刻**からこの計算で求める。ダッシュボードの帰社予定（6.7節）は配達完了の**実績**から求めるため、両者は一致しないことがある

### 6.4 複数便（`tripPlanning.ts`、`routeReorder.ts`）

- 便ごとに順番と到着予定を計算し、2便目以降は前の便の本社帰着＋積み込み時間に出発する
- 割当が変わるたびに、そのルート全体を計算し直して保存する（`reorderRoute`）
- 便を完了して本社へ戻ったら、まだ始まっていない後続の便を、実際の帰着時刻を起点に計算し直す（`rescheduleFollowingTrips`）
- 全停車地が完了・スキップになると、ルートと便を自動で完了にする。配送先が1件もない便は完了扱いにしない

### 6.5 荷物受付の定時超過判定（`timeOverflow.ts`、`dayTimeOverflow.ts`）

その日に登録された内容をすべて配りきるとして、各トラックが定時までに本社へ戻れるかを見積もる（何も保存しない）。

- 未割当の配送先を体積の大きい順に、荷台に入り、到着希望時刻に矛盾せず、積んだ場合に最も早く終わるトラックへ仮に振り分ける
- 各トラックについて、容積上限×積載利用率に達するたびに本社へ戻って積み直す（積み込み時間を加える）として、最後の便の本社帰着時刻を求める
- 荷台に入らない配送先は計算に含めない
- AI提案（6.2）とは別の計算方式で、結果は一致しないことがある

### 6.6 検証（`planValidation.ts`）

- `checkTruckAvailable` / `checkDriverAvailable`: 同じ日に同じトラック・ドライバーが他のルートで使われていないか
- `checkDriverNotOnDayOff`: 配送日がドライバーの休日（土日・祝日・個別休日）でないか
- `validatePackagesInput`: 荷物の入力（寸法など）の検証

### 6.7 ダッシュボードの帰社予定（`returnEstimate.ts` の `estimateReturnEta`）

配達をすべて終え、帰社ボタンがまだ押されていない（帰社途中の）ルートについて、本社に着く見込みの時刻を求める。

- 最後に配達完了を押した停車地の完了時刻（`arrivedAt`。積み下ろしが済んだ時点の記録なので積み下ろし時間は足さない）から、その場所と本社の間の移動時間を足す。昼休みにかかれば休憩明けまで繰り下げる（6.3節と同じ扱い）
- 完了の実績が1件も無い（すべてスキップなど）場合は、予定が最も遅い停車地の予定時刻＋積み下ろし時間から求める

### 6.8 CSVの読み取り（`csvImport.ts`）

配送先・商品のCSV一括登録で共通に使う。

- **文字コード**（`decodeCsv`）: UTF-8として正しく読めればUTF-8（BOMは取り除く）、読めなければShift_JIS（Excelの「CSV（コンマ区切り）」保存）として読む
- **見出し**（`parseCsvTable`）: 1行目に必須の見出し（配送先は名称と住所、商品は商品名・幅・奥行き・高さ）がそろっていれば見出しに従って読み、それ以外の列は無視する。そろっていなければ見出しなしとみなし、決まった列順で1行目から読む。日本語・英語の見出し、大文字・小文字、前後の空白の違いは吸収する
- 値の前後の空白は取り除き、空行は無視する。データが1行も無い（空のファイルなど）場合は400で理由を返す
- 画面側は、ファイルを選んだ後にそのファイルを保存し直して送信できなかった場合（ブラウザの「Failed to fetch」）、ファイルを選び直すよう案内する

| コマンド | 内容 |
|---|---|
| `npm run dev` | 開発サーバーの起動（`tsx server.ts`、既定はポート3000） |
| `npm run build` | 本番用の組み立て（lint・型チェックを含む） |
| `npm start` | 本番起動（`cross-env NODE_ENV=production tsx server.ts`。Windowsでも動く） |
| `npm test` | 自動テストの実行（`TZ=Asia/Tokyo` で実行） |
| `npm run db:migrate` / `npm run db:seed` | DBマイグレーション／初期データ投入 |

- `server.ts` を変更した場合、開発サーバーのホットリロードでは反映されないため再起動が必要
- `tsx` は本番の起動にも使うため `dependencies` に入れている。組み立てに使う `tailwindcss` 等は `devDependencies` のため、組み立ては開発用の部品も入れた状態で行う
- 本番（`NODE_ENV=production`）では、PrismaのログはエラーのみにしてSQLを出さない

### 8.2 環境変数

| 変数 | 内容 |
|---|---|
| `DATABASE_URL` | PostgreSQLの接続先 |
| `NEXTAUTH_URL` | このシステムの正式なURL。本番は `https://...` |
| `NEXTAUTH_SECRET` | ログイン状態の署名に使う秘密の値。本番では推測できない長いランダムな値にする。漏れると管理者になりすませる |
| `HOSTNAME` / `PORT` | 待ち受け設定（既定 `0.0.0.0` / `3000`） |

地図と住所検索にAPIキーは不要。`.env.local` に残る `GOOGLE_MAPS_API_KEY`・`MAPBOX_TOKEN`・`NEXT_PUBLIC_MAPBOX_TOKEN` は使われていない（コメントアウト済み）。

### 8.3 自動テスト

- 対象は計算部分（`src/lib/*.test.ts`）: 積載の判定（荷台寸法の検証・容積上限の計算・積載利用率を含む）、到着予定と昼休み、順番、複数便、AI提案の割当、定時超過の判定、ダッシュボードの帰社予定、CSVの読み取り、ドライバー用URLの有効期限、運行状況・受付状況・編集可能期間の判定
- 時刻は本社の真北に配送先を置いて検証している（経線上の距離は誤差なく求まり、15km＝時速30kmでちょうど30分）
- 計算部分を修正したら `npm test` を実行する。不具合を直したら、その再発を検知するテストを追加する
- 画面操作の自動テストはない

## 9. リアルタイム通信

- `server.ts` でSocket.ioを `/api/socket` で動かす。接続はログイン済み・同じホストからのみ（3.5節）
- サーバーから送るイベント: `tracking:update`（位置情報。`/api/tracking` 受信時）、`tracking:stop-update`（配達状況。`/api/tracking/stops/[id]` 更新時）
- 受信するのはリアルタイム追跡画面の地図だけ。ルート一覧は15秒ごとの再取得、ドライバー画面は30秒ごとの再取得

## 10. 既知の制約・未実装事項

- 手動割当では容積・サイズのチェックをしない（AI提案の表示は参考扱い。現状維持で確定）
- AI提案は稼働前のトラックだけが対象で、稼働中のルートには出さない
- 稼働中のルートでトラックの差し替えはできない（ドライバー変更のみ）
- 運送開始済みのルートを画面から削除する手段はない
- ガントチャートの停車地マーカーは予定時刻の位置に表示する（実績は帰社マーカーのみ反映）。「本社立寄り（積み込み・推定）」マーカーは到着予定から逆算する推定で、昼休みを考慮していない
- 位置情報・給油記録は便ごとに区別して保存しているが、画面の表示は便を区別していない
- DBに保存済みの到着予定時刻は、そのルートが次に並べ替え・保存されるまで、計算ルールの変更（2026-10-14の昼休みの扱いなど）が反映されない
- ドライバー用URLは日本時間の0時で使えなくなる。深夜に及ぶ運行がある場合は見直しが必要
- 荷物受付の定時超過判定とAI提案は別の計算方式で、結果は一致しないことがある
- 本社での積み込み時間（既定30分）は概算値。実際の所要時間が分かったらシステム設定画面で変更する
- 地図画像は OpenStreetMap の公式サーバーを使っている。業務での利用規模と利用規約の確認が必要
- 住所検索で番地まで一致しなかった配送先は、地図上の位置が町・市の代表地点になり、距離・到着予定もその位置で計算される（配送先一覧で注記を表示。番地まで一致する書き方に直すと改善する）
- 帰社予定時刻は、配送計画一覧（予定時刻から計算）とダッシュボード（配達完了の実績から計算）で一致しないことがある
- トラックの積載量（kg）は必須入力だが、計算には使っていない（重量は考慮しない方針）
- 商品のCSV一括登録は同じ名前の商品を登録しないため、寸法の変更には使えない（画面の編集で行う）
